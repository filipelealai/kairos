## Objetivo

Implementar `*yolo` como um **estado de sessão liga/desliga** no `@kairos`. Quando ativado, todos os comandos de conteúdo instanciado (`*new-squad`, `*workers`, `*new-story type: instance`, `*implement`, `*update-squad`) operam de forma totalmente autônoma — sem elicitação, sem confirmações intermediárias, sem handoffs manuais — e avançam automaticamente até o `*pre-push` (inclusive). O push nunca é executado automaticamente.

O modo não persiste entre sessões: encerrar o chat ou abrir um novo desativa o yolo automaticamente.

## Contexto

O fluxo normal do Kairos é interativo por design — elicita, confirma, apresenta ao usuário em cada etapa. Isso é valioso para conteúdo sensível e para quem está aprendendo o framework. Mas para um usuário que já domina o Kairos e quer entregar rápido, o overhead de confirmações manuais é fricção desnecessária.

`*yolo on` é o "confio no teu julgamento, vai fundo" — @kairos toma todas as decisões de arquitetura, cria, implementa, revisa e commita sem interromper. O usuário só precisa saber que o modo está ativo (indicador constante) e que pode desligar a qualquer momento.

**Escopo deliberado: apenas instanciado.** Conteúdo de framework (`type: kairos-core`) continua exigindo interação explícita — o risco de mudanças estruturais sem revisão humana é alto demais para ser automatizado.

**Estado de sessão, não arquivo.** O yolo não é persistido em disco para evitar que o usuário esqueça que está ativado entre sessões ou que um contexto compactado "engula" a desativação. Cada nova sessão começa com yolo OFF.

## Critérios de Aceite

- [x] AC1: `*yolo on` ativa o modo; `*yolo off` desativa; `*yolo` sem argumento exibe o estado atual (ON/OFF)
- [x] AC2: O estado `yolo_active` é mantido exclusivamente em memória de sessão — não é escrito em nenhum arquivo; cada nova sessão do Claude Code começa com `yolo_active = false`
- [x] AC3: Enquanto `yolo_active = true`, toda resposta do @kairos exibe um indicador visível no início: `⚡ YOLO ON — modo autônomo ativo. *yolo off para desativar.`
- [x] AC4: Com yolo ON, os comandos de conteúdo instanciado (`*new-squad`, `*workers`, `*new-story`, `*implement`, `*update-squad`) pulam: elicitação guiada, confirmações intermediárias e handoffs manuais entre sub-etapas — @kairos toma todas as decisões com base na descrição fornecida pelo usuário
- [x] AC5: Com yolo ON, ao concluir qualquer comando instanciado, @kairos encadeia automaticamente `*review` e `*pre-push` sem aguardar instrução do usuário — se o gate retornar BLOCK, @kairos tenta corrigir autonomamente e re-executa `*review`; só pausa e reporta ao usuário se o segundo gate também retornar BLOCK
- [x] AC6: `*push` NUNCA é executado automaticamente, independente do estado do yolo
- [x] AC7: Comandos de framework (`type: kairos-core`: `*new-story kairos-core`, mudanças em tasks, rules, personas) ignoram o yolo — comportamento interativo normal é mantido; @kairos avisa se o usuário tentar usar yolo para isso
- [x] AC8: `*yolo on` exibe aviso único no momento da ativação: lista os comandos afetados, confirma que pre-push será automático e que push permanece manual
- [x] AC9: Persona `@kairos` atualizada com entrada `*yolo` nos comandos (visibility: key) e com a lógica de estado de sessão `yolo_active`

## Fora de Escopo

- Yolo para operações de squads de terceiros fora do `@kairos`

## Dependências

### Decisões tomadas

- **Seção `yolo_mode` no YAML vs task separada:** a lógica do `*yolo` é estado de sessão puro — sem acesso a arquivos externos, sem dependência de task. Colocar inline na persona evita o overhead de carregamento de arquivo e garante que o estado seja sempre parte da definição do agente. Trade-off aceito: a seção fica mais longa, mas é autoexplicativa.
- **`framework_protection` como bloco inline:** a regra de imunidade de `kairos-core` foi colocada dentro do `yolo_mode` em vez de referenciada em `agent-authority.md` — contexto local é suficiente e evita carga adicional de rule na ativação.
- **STEP numerado renomeado:** STEP 5 era "HALT e aguarde input"; agora é "Inicialize yolo_active = false" e STEP 6 é o HALT. A ordem importa — o estado deve ser inicializado antes do agente parar.
