# Story 5.34 — push-dual auto-sync com manifest: lista dinâmica e detecção de remoções

**Epic:** 5
**Status:** Done
**Complexidade:** M
**Tipo:** instance
**Criada por:** @kairos
**Data:** 2026-04-27

## Objetivo

Eliminar a lista hardcoded de arquivos em `push-dual.md`, substituindo-a por leitura dinâmica do `manifest.yaml` em runtime, e adicionar detecção de remoções: arquivos que saem do manifest são removidos de `origin/main` no próximo push.

Hoje, qualquer mudança no manifest exige atualização manual do push-dual. A story remove esse acoplamento — o push-dual passa a ser uma consequência do manifest, não um espelho frágil dele.

## Contexto

`squads/ops/tasks/push-dual.md` mantém três listas hardcoded que devem espelhar o `manifest.yaml`:
- Passo 2a: lista de `git checkout` para `owned_files` e `sync_files`
- Passo 2b: lista de arquivos `owned_sections` e nomes de blocos/seções

Quando o manifest evolui (arquivo adicionado, removido ou renomeado), o push-dual fica desatualizado até atualização manual. A seção "Manutenção" do push-dual documenta esse ônus — que esta story elimina.

## Critérios de Aceite

- [x] Passo 2a do push-dual não contém mais lista hardcoded de caminhos: a instrução ao agente é ler `manifest.yaml → owned_files[].path` e `manifest.yaml → sync_files[].path` em runtime e executar `git checkout filipe-instance -- <path>` para cada um
- [x] Passo 2b do push-dual não contém mais lista hardcoded de arquivos nem de nomes de blocos/seções: a instrução é derivar `manifest.yaml → owned_sections` em runtime (path + type + blocks/owned_sections/owned_keys conforme o tipo), aplicando a lógica de reconstrução existente por tipo de arquivo
- [x] Um passo de detecção de remoções é adicionado **antes** do Passo 2a: compara os arquivos tracked em `main` (via `git ls-files`) contra o conjunto completo de paths do manifest atual (owned_files + sync_files + paths de owned_sections); qualquer arquivo tracked não presente no manifest é removido com `git rm` antes da sincronização
- [x] Se o passo de detecção encontrar remoções, elas são incluídas no commit do Passo 3 junto com os arquivos atualizados; se não houver remoções nem atualizações, o comportamento de skip já existente é mantido
- [x] A seção "Manutenção" do push-dual é removida
- [x] O restante do comportamento do push-dual permanece inalterado: guard obrigatório, pré-condições, skip por conteúdo idêntico em Passo 2b, resumo de Passo 2b, Passo 1, Passo 3, Passo 4, Passo 5, tabela de erros comuns

## Fora de Escopo

- Mudanças na lógica de reconstrução de cada tipo de `owned_sections` (markdown_blocks, yaml_keys, env_sections) — a lógica de reconstrução permanece igual, apenas a lista de arquivos passa a vir do manifest
- Qualquer mudança no `manifest.yaml`
- Qualquer arquivo fora de `squads/ops/tasks/push-dual.md`
- Criação de script externo ou helper — a leitura do manifest é feita inline pelo agente (Claude Code) ao executar `*push`, sem ferramenta adicional

## Dependências

- `squads/ops/tasks/push-dual.md` — arquivo a ser modificado (user-owned, instância)
- `.kairos-core/manifest.yaml` — fonte de verdade que o push-dual passará a ler dinamicamente

### Decisões tomadas

- **`git show` vs leitura direta do arquivo:** quando em `main`, o manifest do working directory é a versão de `main` (possivelmente desatualizada). Usar `git show filipe-instance:.kairos-core/manifest.yaml` garante sempre a versão atual de `filipe-instance`, sem depender da ordem dos passos.
- **`git add -A` no Passo 3:** necessário para capturar tanto os arquivos novos/modificados quanto as remoções do Passo 2.0 (que ficam staged pelo `git rm` mas precisam estar no mesmo commit). O comportamento anterior usava `git add <arquivos modificados>` — o `git add -A` é seguro porque em `main` só existem arquivos framework (por design).
- **manifest_all_paths inclui owned_sections:** para o passo de detecção de remoções, é necessário incluir os paths de `owned_sections` no conjunto de paths válidos — caso contrário, CLAUDE.md, core-config.yaml e .env.example seriam erroneamente removidos de `main`.
