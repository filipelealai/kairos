## Objetivo

Completar o suporte a `owned_sections` nos três arquivos mistos do framework: adicionar markers estruturais onde faltam, SHA por bloco/chave/seção no manifest, sync no push-dual e validação no doctor — habilitando detecção de drift e preparando o terreno para o updater futuro.

## Contexto

Hoje, `owned_sections` cobre três arquivos (CLAUDE.md, core-config.yaml, .env.example), mas cada um tem gaps diferentes:

| Arquivo | No manifest | Markers no arquivo | SHA por bloco | Tratado no push-dual Passo 2b |
|---------|------------|-------------------|---------------|-------------------------------|
| CLAUDE.md | ✓ (markdown_blocks) | ✓ KAIROS-MANAGED-START/END | ✗ | ✓ |
| core-config.yaml | ✓ (yaml_keys) | n/a (chaves YAML) | ✗ | ✓ |
| .env.example | ✓ (env_sections) | ✗ apenas comentários | ✗ | ✗ |

Sem SHA por bloco, um futuro updater não tem como saber se uma seção managed está desatualizada. Identificado durante discussão pós-stories 5.8/5.9.

**Nota sobre consistência entre repos:** SHAs de `owned_sections` rastreiam apenas o conteúdo dos blocos framework-owned — exatamente o que push-dual Passo 2b copia de `filipe-instance` para `main`. Após sync, ambos os repos têm o mesmo conteúdo nos blocos → mesmo SHA. Sem inconsistência entre branches.

### Decisões tomadas

- **SHA do conteúdo interno vs SHA do bloco completo (com markers):** escolhemos conteúdo interno (excluindo markers) — os markers são estrutura, não conteúdo. O updater compara somente o que importa semânticamente, não a linha de marcação.
- **`sha256_by_key` vs campo inline por chave:** usamos `sha256_by_key` como dict separado em vez de lista de objetos `{name, sha256}` para manter `owned_keys` como lista simples (compatibilidade com o push-dual que a lê diretamente) e os SHAs como bloco separado de fácil leitura.
- **`owned_sections` de `.env.example` migrou para lista de objetos:** a lista simples de strings não comporta o campo `sha256`; migrar para `{name, sha256}` era necessário e não quebra o push-dual (que opera por nome).
