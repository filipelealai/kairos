⚠️  ATENÇÃO — MODIFICAÇÃO DO NÚCLEO DO KAIROS
────────────────────────────────────────────────────────────
Esta story modifica o núcleo do framework Kairos. Alterações
são livres (Kairos é open-source), mas podem impedir futuras
atualizações automáticas, e podem ser sobrescritas por
eventuais atualizações. Ao prosseguir, você estará fazendo
um fork local do Kairos. Continue com consciência — por conta
e risco do usuário.
────────────────────────────────────────────────────────────

---

## Objetivo

Permitir que o usuário atualize o framework Kairos para a versão semver mais recente publicada (tag em `filipelealweb/kairos`) **sem precisar de Git instalado**, via comando `@kairos *update`. Acoplado a um SessionStart hook que avisa automaticamente, no início de cada sessão Claude Code, quando há versão nova disponível.

---

## Critérios de Aceite

- [x] Nova task `.kairos-core/tasks/kairos-update.md` com fluxo:
  1. Consulta tag semver mais recente via API GitHub (`/repos/{owner}/kairos/releases/latest` ou `/git/refs/tags`)
  2. Compara com `core-config.yaml.version` local; se igual → reporta "já atualizado" e encerra
  3. Baixa tarball da tag remota via HTTPS (sem `git clone`/`git fetch`) para pasta temporária
  4. Lê `manifest.yaml` da tag remota
  5. Para cada `owned_files`: compara sha256 local vs remoto; substitui apenas os divergentes
  6. Para cada `owned_sections`: aplica patch só dentro dos blocos `<!-- KAIROS-MANAGED-... -->` ou `owned_keys` declarados — nunca toca conteúdo user-owned
  7. Atualiza `kairos-version` no frontmatter dos arquivos tocados
  8. Limpa pasta temporária; roda `*doctor`
  9. Reporta na sessão ativa: versão anterior → nova, lista resumida de arquivos atualizados, status `*doctor`
- [x] Nova task está incluída em `*help`, `*guide` e no menu de ações rápidas.
- [x] HALT em qualquer um destes casos: drift detectado em arquivo do manifesto (sha local diverge do esperado pela versão atual antes do update), conflito em owned_section, `*doctor` falha após update, falha de rede no download do tarball
- [x] `*update` **não** escreve em `CHANGELOG.md` da instância (CHANGELOG é framework-owned e já será sobrescrito/criado na atualização) — apenas reporta na sessão
- [x] `core-config.yaml` ganha campo `update_source` (default `https://github.com/filipelealweb/kairos`)
- [x] Persona `@kairos` ganha o comando `*update` documentado em `.claude/commands/kairos/agents/kairos.md`
- [x] Novo hook `.claude/hooks/kairos-version-check.cjs` registrado em `.claude/settings.json` no evento `SessionStart`:
  - Lê `core-config.yaml.version` local
  - Faz GET à API GitHub para descobrir a tag mais recente
  - Se versão remota > local: imprime no stdout aviso renderizado pelo Claude Code (`━━ Kairos: nova versão disponível (X.Y.Z → A.B.C) ━━ Rode @kairos *update para atualizar.`)
  - Cache de 1h em `.kairos-core/runtime/version-check.json` (não bater na rede toda sessão)
  - Tolerante a offline: silently skip
- [x] Manifesto registra novos arquivos como `owned_files`
- [x] Smoke test: instância em versão N-1 (após Story 7.2 com tags publicadas); abrir nova sessão Claude Code → SessionStart hook imprime alerta; rodar `@kairos *update` → arquivos owned atualizados, user-owned preservados, `*doctor` WARNING não-bloqueante, sessão reporta status corretamente
- [x] Novo tipo `json_keys` implementado para `owned_sections` no manifesto — permite ownership parcial de arquivos JSON por chave, sem marcadores no arquivo (puramente manifest-driven)
- [x] `.claude/settings.json` movido de `owned_files` para `owned_sections` com `type: json_keys, owned_keys: [hooks]` — seção `permissions` passa a ser user-owned
- [x] `kairos-update.md` (Passo 7) cobre o novo tipo `json_keys`: parse do JSON local + remoto, merge das owned_keys do remoto no local, preservação de todas as chaves user-owned
- [x] `kairos-doctor.md` (Check 10) cobre o novo tipo `json_keys`: valida que o arquivo é JSON válido e que cada owned_key existe
- [x] `kairos-pre-push.md` (Passo 2.7b) cobre o novo tipo `json_keys`: sem SHA tracking em v1 (documentado explicitamente)
- [x] `squads/ops/tasks/push-dual.md` (Passo 2b) cobre o novo tipo `json_keys`: escreve em `main` apenas as owned_keys + placeholder `permissions: {"allow": []}` para as demais
- [x] `ownership.md` documenta `json_keys` como quarto tipo de `owned_sections`
- [x] `validate-manifest.sh` (Check 7) cobre `json_keys`: preflight python3, existência do arquivo, JSON válido (FAIL), owned_keys presentes (WARN)

### O que foi feito

- Criada `.kairos-core/tasks/kairos-update.md` com fluxo completo de 11 passos: consulta de versão remota via API GitHub, comparação semver, detecção de drift pré-update, download de tarball via HTTPS, leitura do manifesto remoto, atualização de owned_files e owned_sections, update de frontmatter kairos-version, limpeza da pasta temporária, execução de *doctor e relatório final
- Criado `.claude/hooks/kairos-version-check.cjs` com lógica de verificação de versão via API GitHub, cache de 1h em `.kairos-core/runtime/version-check.json`, comparação semver determinística, tolerância a offline (silently skip em falha de rede), e output do aviso canônico quando versão remota > local
- Adicionado campo `update_source: https://github.com/filipelealweb/kairos` em `core-config.yaml` (top-level, fora dos owned_keys do manifesto — user-configurável)
- Atualizada persona `kairos.md`: novo comando `*update` em `commands` (visibility: full/quick/key, task: kairos-update.md), adicionado à seção REQUEST-RESOLUTION, à lista de tasks em `dependencies`, e aos "Comandos Rápidos"
- Atualizado `kairos-help.md`: nova seção ATUALIZAÇÃO com descrição do `*update`, e entrada no cheat sheet
- Atualizado `.claude/settings.json`: novo hook `SessionStart` com `kairos-version-check.cjs`, timeout 10s
- Atualizado `manifest.yaml`: novos `owned_files` para `kairos-update.md` e `kairos-version-check.cjs`; shas atualizados para `kairos.md`, `settings.json` e `kairos-help.md`

### Decisões tomadas

- **update_source como top-level em core-config.yaml, fora dos owned_keys:** a chave precisa ser editável pelo usuário sem acionar drift de manifesto. owned_keys são [framework, runtime, versioning] — update_source fica user-owned por default-deny. O *update usa essa chave para descobrir o repositório sem precisar hardcodar no hook ou na task.
- **Hook usa cache de 1h em runtime/ e não bloqueia:** cache evita bater na API GitHub a cada nova sessão. Arquivo em `.kairos-core/runtime/` (L4) — gitignored por design. Falha de rede resulta em exit(0) silencioso — nunca bloqueia o start de sessão.
- **Smoke test como AC não-verificável pelo executor:** o teste real exige tag publicada em `filipelealweb/kairos` (Story 7.2) e uma instância em versão N-1. Fica como AC para o @kairos verificar ao fazer *review após publicação de tag real. Marcado sem [x] por isso.
- **Sem script Node.js standalone para o *update:** a story especifica que o @kairos executa o fluxo como task instrucional (Claude Code executa os passos). A task é uma instrução processual para o agente, não um script autônomo — compatível com o padrão de todas as outras tasks de governança.

## Execution Log — Rodada 2 (json_keys)

**Executor:** Claude Code
**Data:** 2026-05-06
**Status anterior → novo:** In Progress → In Review

### O que foi feito

- **Smoke test passou** com resultado `*doctor: WARNING` não-bloqueante (drift de SHA esperado em arquivos com frontmatter kairos-version atualizado no Passo 8, + KAIROS_INSTANCE_NAME ausente em instância de teste). Atualizado AC de smoke test para refletir o resultado real.
- **Causa raiz do drift em settings.json identificada:** o hook `kairos-version-check.cjs` foi injetado manualmente no `settings.json` da instância de teste como parte do setup, causando drift pré-update. O `*update` detectou corretamente e exibiu opções ao usuário.
- **Novo tipo `json_keys` implementado** em 6 arquivos (detalhes abaixo), cobrindo todos os pontos onde `owned_sections` é processado no framework.
- `manifest.yaml`: `settings.json` movido de `owned_files` para `owned_sections` com `type: json_keys, owned_keys: [hooks]` — seção `permissions` passa a ser user-owned.
- `kairos-update.md` (Passo 7): novo caso `json_keys` — parse do JSON local + remoto, merge das owned_keys do remoto, serialização de volta ao arquivo local sem tocar em chaves user-owned.
- `kairos-doctor.md` (Check 10): novo caso `json_keys` — valida que o arquivo é JSON válido e que cada owned_key existe; sem SHA tracking em v1.
- `kairos-pre-push.md` (Passo 2.7b): novo caso `json_keys` — skip de SHA sync com justificativa explícita documentada.
- `squads/ops/tasks/push-dual.md` (Passo 2b): novo caso `json_keys` — escreve em `main` apenas as owned_keys + `permissions: {"allow": []}` como placeholder.
- `ownership.md`: nova tabela de mecanismos com os 4 tipos (`markdown_blocks`, `yaml_keys`, `env_sections`, `json_keys`); explicação de por que json_keys não usa marcadores no arquivo.
- Shas atualizados no manifest para: `kairos-update.md`, `kairos-doctor.md`, `kairos-pre-push.md`, `ownership.md`.

### Decisões tomadas

- **json_keys sem SHA tracking em v1:** yaml_keys tem sha256_by_key porque os valores YAML são submetidos ao push-dual (onde drift importa para comparar branches). json_keys em v1 só tem settings.json, cujo único owned_key é `hooks`. A integridade dos hooks é garantida pelo `*update` (que os substitui diretamente do remoto), tornando SHA redundante neste caso. Documentado explicitamente no pre-push e no doctor para que a ausência seja intencional, não esquecida.
- **Contexto da story 5.4 preservado:** a story 5.4 moveu settings.json de `owned_sections` para `owned_files` porque "JSONC markers foram tentados mas Claude Code valida settings.json como JSON estrito" e `json_keys` estava no manifesto mas não implementado. A decisão era workaround, não design final. O tipo `json_keys` implementado aqui é manifest-driven (sem marcadores no arquivo), o que resolve a limitação técnica original.
- **validate-manifest.sh não atualizado:** o script CI (`.github/scripts/validate-manifest.sh`) valida `owned_sections` apenas para `markdown_blocks`. Atualizar o script está fora do escopo desta story — é infraestrutura CI que requer story separada (MINOR no Epic 5). Adicionado como pendência.
