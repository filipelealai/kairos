## Notas de Implementação

**Sobre a ordem dos passos:** o plano em `squads/ops/tasks/mcp-deploy.md` descreve 12 passos sequenciais. Seguir nessa ordem evita retrabalho — em particular, criar os secrets antes do `docker stack deploy` é necessário pro deploy não falhar.

**Sobre o Service Account:** o usuário sinalizou que vai precisar de assistência. O fluxo no Google Cloud Console é interativo e tem várias telas — é razoável o `@kairos` (executor desta story via `*implement`) acompanhar passo a passo, mas a clicagem efetiva nos botões precisa ser feita pelo usuário. O JSON da chave será baixado pelo browser dele.

**Sobre a Personal Access Token:** o usuário gera no GitHub. Idealmente um token de escopo mínimo (`repo` apenas no `kairos-pessoal`, ou fine-grained com permissão só de Contents:Read).

**Sobre a `GOOGLE_DRIVE_ROOT_FOLDER_ID`:** essa não vai como Docker secret porque não é credencial — é só um identificador de pasta. Pode ir como env var direto no compose (interpolação `${...}`) ou como secret também, conforme preferência. O atual `docker-stack.yml` espera env var.

**Sobre rollback:** o plano inclui passo de rollback. Importante validá-lo (mesmo sem chamar de "AC formal") porque a primeira hora pós-deploy é onde tudo pode dar errado. `docker stack rm kairos` é idempotente.

**Sobre validação com membro do time:** não basta um teste técnico (curl). O membro real precisa abrir o Claude Desktop, ver o servidor aparecer, executar um agente, ver o output aparecer no Drive dele. Isso valida a UX completa do guia em `squads/team-setup.md`.

### Decisões tomadas

- **Push direto via git em vez de `*push` formal durante o ciclo da story:** o protocolo `*push` requer `*pre-push` PASS, que requer story em In Review com gate. Mas o pivot OAuth no meio da story exigia que o código novo estivesse em `kairos-pessoal/filipe-instance` antes de buildar nova imagem na VPS. Decisão pragmática: commit + push direto, documentado aqui como exceção declarada. O ciclo formal `*review`→`*pre-push`→`*push` será retomado a partir desta story (sem pendências de código não-comitado).

- **Cloudflare proxy ON com cert próprio em vez de Let's Encrypt no origin:** v1 aceita TLS terminado no Cloudflare. Trade-off: CF↔origin pode ser HTTP cleartext interno (depende do modo de SSL configurado no CF). Pra v2 ou se ficar claro que precisa de TLS end-to-end auditável, trocar pra Cloudflare Origin Certificates ou desabilitar proxy temporariamente pra emitir LE.

- **OAuth Desktop app + redirect_uri loopback** em vez de Web app + redirect_uri público: Desktop app aceita qualquer porta loopback como redirect, ideal pra script local. Sem necessidade de hospedar callback público.

- **Refresh token armazenado como Docker secret JSON único** (`{client_id, client_secret, refresh_token}`) em vez de 3 secrets separados: mais compacto, atomicamente rotacionável, e o cliente OAuth da `googleapis` espera essa estrutura.

- **Cloudflare para frente do Traefik** em vez de bypass com gray cloud: usuário já tinha CF proxy ON. Trade-off documentado acima. Mantido por simplicidade.

- **Rollback parcialmente exercitado:** `docker stack rm kairos` foi executado durante o redeploy do código OAuth (limpou serviço, manteve rede e secrets). Não foi feito teste destrutivo total (que derrubaria o serviço por completo) por já termos validação end-to-end pendente; aceito como ressalva.
