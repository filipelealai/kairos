## Objetivo

Concretizar em produção o servidor MCP cuja implementação foi entregue na Story 6.1: criar Service Account no Google Cloud, gerar GitHub PAT para acesso ao repo privado, configurar secrets no Docker Swarm da VPS, fazer build da imagem, deployar o stack via Easypanel, validar HTTPS via Traefik+Let's Encrypt, e validar end-to-end com pelo menos um membro do time conectando o Claude Desktop e operando um pipeline de squad real.

A entrega valida que o caminho completo funciona: `time member → Claude Desktop → MCP server na VPS → squad executa → output no Drive`.

## Critérios de Aceite

- [ ] **GitHub PAT criado** com escopo `repo` (read-only suficiente) e validado: `git clone https://<PAT>@github.com/filipelealweb/kairos-pessoal.git` funciona em ambiente de teste
- [ ] **Service Account do Google Cloud criada** seguindo `squads/ops/tasks/mcp-deploy.md` passo 3:
  - Projeto Google Cloud (novo ou existente)
  - Drive API habilitada
  - Service Account `kairos-mcp-server` criada
  - JSON key gerada e armazenada em local seguro
  - Pasta-raiz no Drive (ex: "Kairos Outputs") criada e compartilhada com o e-mail da Service Account em modo **Editor**
  - ID da pasta-raiz capturado da URL
- [ ] **API key do MCP gerada** via `openssl rand -hex 32` (64 chars hex), armazenada em local seguro pelo usuário
- [ ] **Docker secrets criados na VPS** via SSH:
  - `kairos_mcp_api_key` (a key do passo anterior)
  - `kairos_drive_sa` (o JSON da Service Account)
  - `kairos_git_url` (URL do repo com PAT embutido)
  - `docker secret ls` lista os 3
- [ ] **Imagem `kairos-mcp:latest` buildada na VPS** a partir do código de `kairos-pessoal/filipe-instance` — `docker images kairos-mcp:latest` mostra a imagem
- [ ] **Stack `kairos` deployado via `docker stack deploy`** com `GOOGLE_DRIVE_ROOT_FOLDER_ID` injetado por env var:
  - `docker stack services kairos` mostra `kairos_kairos-mcp` com 1/1 replicas
  - `docker service logs kairos_kairos-mcp --tail 50` mostra: clone bem-sucedido, agentes operacionais carregados, Drive client habilitado, "Kairos MCP Server listening"
- [ ] **HTTPS via Traefik + Let's Encrypt funcionando:**
  - `curl -fsS https://kairos.vendoteca.com/health` retorna 200 com JSON `{ok:true,...}`
  - Certificado válido (não auto-assinado)
- [ ] **Smoke test do MCP em produção:**
  - `POST /mcp` com header `Authorization: Bearer <api-key>` e body de `initialize` retorna `protocolVersion`, `capabilities`, `serverInfo`
  - `POST /mcp` com `prompts/list` retorna os 10 prompts esperados
  - `POST /mcp` sem header retorna 401
- [ ] **Sincronização periódica funcionando:**
  - Após push em `kairos-pessoal/filipe-instance`, o contêiner reflete a mudança em ≤ 60 segundos sem restart manual
  - Validado modificando um arquivo de teste no repo, fazendo push, e verificando via tool MCP que o conteúdo atualizou
- [ ] **Validação end-to-end com membro do time:**
  - Pelo menos um membro do time (não o owner do framework) instala Claude Desktop
  - Configuração JSON de `claude_desktop_config.json` aplicada com sucesso
  - Servidor `kairos` aparece no menu de prompts MCP do Claude Desktop
  - Membro executa um pipeline operacional (sugestão: `kairos-client-onboarding-brief-extractor` com input fictício de uma empresa)
  - Output gerado pelo agente:
    - Salvo no contêiner em `data/outputs/{squad}/{subdir}/`
    - Sincronizado pra pasta correspondente no Drive
    - Visível pelo membro do time no Drive
  - Documentar a validação no Execution Log com nome/identificador do membro, agente usado, e link do output no Drive
- [ ] **Atualização da `squads/team-setup.md`** com qualquer aprendizado da validação real (troubleshooting, observação de comportamento, etc.) — deve ser feita ao final, não antes
- [ ] **Plano de rollback testado** — `docker stack rm kairos` derruba o stack limpo; o repo no GitHub e a pasta no Drive não são afetados

## Notas de Implementação

**Sobre a ordem dos passos:** o plano em `squads/ops/tasks/mcp-deploy.md` descreve 12 passos sequenciais. Seguir nessa ordem evita retrabalho — em particular, criar os secrets antes do `docker stack deploy` é necessário pro deploy não falhar.

**Sobre o Service Account:** o usuário sinalizou que vai precisar de assistência. O fluxo no Google Cloud Console é interativo e tem várias telas — é razoável o `@kairos` (executor desta story via `*implement`) acompanhar passo a passo, mas a clicagem efetiva nos botões precisa ser feita pelo usuário. O JSON da chave será baixado pelo browser dele.

**Sobre a Personal Access Token:** o usuário gera no GitHub. Idealmente um token de escopo mínimo (`repo` apenas no `kairos-pessoal`, ou fine-grained com permissão só de Contents:Read).

**Sobre a `GOOGLE_DRIVE_ROOT_FOLDER_ID`:** essa não vai como Docker secret porque não é credencial — é só um identificador de pasta. Pode ir como env var direto no compose (interpolação `${...}`) ou como secret também, conforme preferência. O atual `docker-stack.yml` espera env var.

**Sobre rollback:** o plano inclui passo de rollback. Importante validá-lo (mesmo sem chamar de "AC formal") porque a primeira hora pós-deploy é onde tudo pode dar errado. `docker stack rm kairos` é idempotente.

**Sobre validação com membro do time:** não basta um teste técnico (curl). O membro real precisa abrir o Claude Desktop, ver o servidor aparecer, executar um agente, ver o output aparecer no Drive dele. Isso valida a UX completa do guia em `squads/team-setup.md`.
