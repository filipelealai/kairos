## Objetivo

Permitir que stories `type: instance` sejam marcadas como Done diretamente em `*implement` e `*review`, sem depender do pipeline Git (`*push`). Após a Story 3.31, a transição Done migra para o `*push` (Passo 1), que é Git-dependente. Isso impede que usuários sem Git (ou que não queiram commitar imediatamente) concluam stories. Esta story adiciona um prompt Done opcional ao final de `*implement` e `*review` para stories de instância, desacoplando a conclusão da story do pipeline de release.

## Contexto

### Situação atual (pré-3.31)

A transição In Review → Done é exclusiva do `*pre-push`. Não existe forma de marcar Done fora do pipeline Git.

### Situação pós-3.31

A transição Done migra para `*push` Passo 1 (antes do commit). Continua acoplada ao Git.

### Problema

Instâncias que não usam Git (ou que não querem commitar imediatamente) não podem marcar stories como Done. Isso afeta:
- Usuários que usam o Kairos apenas como orquestrador, sem repositório Git
- Sessões exploratórias onde o usuário quer iterar e fechar stories sem push
- Cenários de YOLO mode (Story 3.32) onde o release é desacoplado

### Solução

Adicionar prompt Done **opcional e contextual** nos comandos que já sabem o estado da story:

- `*implement` (sempre `type: instance` — o Kairos não se auto-implementa, cf. constitution.md): ao concluir, sugere `*review {id}` como opcional + pergunta "marcar como Done?"
- `*review` (para stories instance com PASS/RESSALVA): ao final, pergunta "marcar como Done?"

Para `type: kairos-core`: nada muda — Done continua exclusivo do pipeline `*push`.

## Critérios de Aceite

### *implement — Sugestão de review + prompt Done

- [x] `kairos-implement.md` ao final da implementação de uma story `type: instance`, exibe bloco de sugestão:
  ```
  ✅ Implementação concluída — Story {id}

  {resumo dos arquivos criados/modificados}

  💡 Opcional: rode *review {id} para validar a implementação
  📋 Marcar story {id} como Done? (s/n)
  ```
- [x] Se `s`: executar lógica de transição Done (ver "Lógica compartilhada" abaixo)
- [x] Se `n`: story permanece `In Review` (status já transicionado pelo `*implement`), sem mensagem adicional
- [x] Para stories `type: kairos-core`: **não exibir** o prompt Done (fluxo completo com `*push` permanece obrigatório)

### *review — Prompt Done após PASS/RESSALVA

- [x] `kairos-review.md` ao final de um review com verdict PASS ou RESSALVA para story `type: instance`, exibe prompt:
  ```
  {relatório de review normal}

  📋 Marcar story {id} como Done? (s/n)
  ```
- [x] Se `s`: executar lógica de transição Done
- [x] Se `n`: story permanece `In Review` (status já transicionado pelo `*implement`), sem mensagem adicional
- [x] Para stories `type: kairos-core`: **não exibir** o prompt Done (pipeline `*push` obrigatório)
- [x] Para verdict BLOCK: **não exibir** o prompt Done (story precisa de correção)

### Lógica compartilhada de transição Done

- [x] Ao marcar Done, executar:
  1. Atualizar campo `**Status:**` na story para `Done`
  2. Adicionar entrada no Change Log da story: `| {data} | Marcada como Done via *{comando} |`
  3. Atualizar status da story na tabela do epic correspondente (`docs/epics/epic-{N}-*.md`)
- [x] Exibir confirmação:
  ```
  ✅ Story {id} marcada como Done.
  
  Próximo: *push (quando quiser commitar) | continuar com outro comando
  ```
- [x] A lógica de transição Done deve ser reutilizável — chamada por `*implement`, `*review`, e `*yolo` (Story 3.32)

### Coexistência com *push

- [x] Se o usuário já marcou a story como Done via `*implement` ou `*review`, o `*push` (Passo 1 pós-3.31) detecta que o status já é Done e **pula** a transição — não tenta transicionar novamente
- [x] Arquivos da story marcada como Done (`.story.md` e epic) ficam como mudanças locais não commitadas — o `*push` os inclui normalmente no commit quando o usuário decidir empurrar

### Guard de tipo

- [x] O prompt Done **só aparece** para stories `type: instance`
- [x] Stories `type: kairos-core` seguem o pipeline completo: `*review` → `*pre-push` → `*push` (que faz Done no Passo 1)
- [x] Se a story não tem campo `type` (compatibilidade retroativa): tratar como `instance` (default seguro)

### Decisões tomadas

- **Lógica compartilhada de transição Done no kairos-implement.md, não em arquivo separado:** a story pede que a lógica seja "reutilizável — chamada por `*implement`, `*review`, e `*yolo`". Optou-se por definir a seção canônica em `kairos-implement.md` e referenciar dela em `kairos-review.md`, evitando duplicação e sem criar novo artefato. Alternativa (arquivo separado `kairos-done.md`) foi descartada — viola o princípio IDS (ADAPTAR > CRIAR).
- **`*review` referencia a lógica de `kairos-implement.md` em vez de duplicar:** mantém ponto único de verdade. Trade-off: quem lê `kairos-review.md` precisa navegar até `kairos-implement.md` para ver os detalhes da transição — aceitável, pois o fluxo é simples e os 4 passos são descritos inline.
- **AC "Chamar `*architecture`" deixado como pendente:** é um AC de validação que requer execução do agente @kairos, não implementação de código. Marcado como pendente no Execution Log para ser resolvido na revisão.
