## Objetivo

Tornar o setup de cloud sync robusto em todos os ambientes suportados: detectar automaticamente apps de cloud por OS, conduzir wizard rclone em Linux/WSL onde apps nativos não existem, eliminar entrada manual de path absoluto trocando-a por escolha de subpasta dentro de um root já detectado, e tolerar latência de cold start de mounts cloud na validação do symlink.

## Contexto

Continuação direta da Story 7.6. A Fase 1 (já implementada nos installers) fechou o bug latente de `cloud-sync.json` ausente, adicionando menu numerado de provedor e gravação do JSON após o symlink. Resolveu o estado, mas manteve UX frágil:

- O usuário ainda digita path absoluto inteiro (alta chance de erro de typo, especialmente em paths com espaço).
- Linux/WSL sem orientação para rclone — usuário típico tenta linkar, por exemplo, para `/mnt/g/` (Google Drive Desktop visto do WSL) e bate em falhas silenciosas de DrvFs.
- Validação do symlink (`echo > .sync-test && cat`) executa imediatamente após `ln -s`. Mounts rclone podem estar dormindo (cold start de 10–30s) e devolver falso negativo.
- Provedor coletado por menu manual não infere automaticamente o que o sistema já sabe.

Esta story corrige os quatro pontos.

## Critérios de Aceite

- [x] **Detecção automática por OS no installer.** [install.sh](install.sh) e [install.ps1](install.ps1) escaneiam paths canônicos por OS e listam apenas provedores encontrados no menu (mais "Outro/Custom", "Configurar com rclone" e "Pular e configurar depois com `@kairos *configure-cloud`" como opções sempre disponíveis). Mapeamento mínimo:
  - Windows: Google Drive (`%USERPROFILE%\Google Drive\Meu Drive`, `G:\Meu Drive`, `H:\Meu Drive`), OneDrive (`%OneDrive%`, `%USERPROFILE%\OneDrive*`), Dropbox (`%USERPROFILE%\Dropbox`, `%LOCALAPPDATA%\Dropbox\info.json`).
  - macOS: iCloud (`~/Library/Mobile Documents/com~apple~CloudDocs`), Google Drive (`~/Library/CloudStorage/GoogleDrive-*/Meu Drive`, `~/Google Drive`), OneDrive (`~/Library/CloudStorage/OneDrive-*`, `~/OneDrive`), Dropbox (`~/Dropbox`, `~/Library/CloudStorage/Dropbox`).
  - Linux/WSL: sem detecção direta — oferece o fluxo rclone (ver AC abaixo) como única opção de configuração no instalador, ou a opção de configurar depois com `@kairos *configure-cloud`.
- [x] **Wizard rclone (Linux, WSL, ou opção manual).** Quando OS = Linux/WSL e/ou usuário escolhe "rclone" no menu:
  - Verifica `command -v rclone`; se ausente, instrui instalação por OS (Linux/WSL: `curl https://rclone.org/install.sh | sudo bash`; macOS: `brew install rclone`) e faz HALT até confirmação.
  - Lista remotes via `rclone listremotes`; se vazio, instrui `rclone config` (interativo, OAuth do rclone) e HALT.
  - Detecta mounts ativos via `mount | grep -E 'type fuse\.rclone'`.
  - Se nenhum mount ativo para o remote escolhido, sugere comando de mount com flags recomendadas (`--vfs-cache-mode writes --dir-cache-time 5s --poll-interval 5s --daemon`) e oferece gravar snippet de persistência.
  - Provider é gravado em `cloud-sync.json` como `rclone:{remote}` (ex: `rclone:drive`).
- [x] **Escolha de subpasta em vez de path absoluto.** Após root detectado (ou mount rclone confirmado), o installer e a task perguntam apenas o nome da subpasta dentro do root, com default "Kairos Outputs". `symlink_target` é montado como `{root}/{subpasta}` e a subpasta é criada se não existir. A opção "Outro/Custom" continua disponível e permite digitar path absoluto inteiro (fallback do comportamento da Fase 1).
- [x] **Fallback total.** Se a varredura não encontra nenhum app de cloud E usuário não está em Linux/WSL, exibe menu de 4 opções: (1) instalar app e voltar, (2) configurar com rclone, (3) path manual, (4) pular e configurar depois com `@kairos *configure-cloud`.
- [x] **Persistência do mount rclone por ambiente.** O wizard verifica systemd via `systemctl is-system-running`:
  - Se ativo (Linux puro ou WSL2 com systemd): oferece `systemd --user` unit (default — sem sudo) ou system-wide unit (com sudo).
  - Se ausente: oferece (a) instrução de habilitar systemd no WSL via `/etc/wsl.conf` + `wsl --shutdown`, ou (b) fallback `.bashrc` com bloco delimitado pelo marcador `# KAIROS-RCLONE-MOUNT` (idempotente — segunda execução não duplica). Aviso explícito de que `.bashrc` só roda em terminal interativo, não funciona com hooks/cron.
- [x] **Reescrita de `kairos-configure-cloud.md`.** A task espelha o fluxo conversacional:
  - Passo 1 vira "Detecção automática" — roda scan, mostra provedores encontrados, oferece escolha ou "Outro".
  - Novo Passo 1.5 condicional: "Wizard rclone" quando OS = Linux/WSL e/ou usuário escolheu rclone.
  - Passo 2 vira "Subpasta" (não path absoluto).
  - Passo 4 (provedor declarado) só pergunta quando detecção é ambígua (múltiplos roots encontrados — ex: dois `GoogleDrive-{conta}` no mesmo Mac).
- [x] **Validação com tolerância a cold start.** Tanto o Passo 7 de [`kairos-configure-cloud.md`](.kairos-core/tasks/kairos-configure-cloud.md) quanto o Check 12 de [`kairos-doctor.md`](.kairos-core/tasks/kairos-doctor.md) usam polling com backoff `1s/2s/5s/10s/15s` (total ≤30s) quando o `provider` é `rclone:*` ou um provedor cloud reconhecido. Tick de sucesso → PASS imediato. Janela esgotada → reportar provável cold start, oferecer retry. Para `custom` e paths locais não-cloud, manter validação rápida (sem polling) para evitar latência desnecessária.
- [x] **Resolução correta de symlinks.** Validações usam `readlink -f` para resolver destino físico ao testar acessibilidade; reportes ao usuário usam `realpath -L` (preserva o caminho do symlink, não troca pelo target). Equivalente PowerShell: `Resolve-Path` (com `-Relative` quando aplicável) e `(Get-Item).Target`.
- [x] **Idempotência.** Rodar installer ou wizard duas vezes consecutivas:
  - Não duplica bloco no `.bashrc` (busca pelo marcador `# KAIROS-RCLONE-MOUNT` antes de gravar).
  - Não quebra symlink existente — detecta `data/outputs` já como symlink e oferece reconfiguração explícita.
  - Reescreve `cloud-sync.json` com novo timestamp em `configured_at`, mantendo formato.
- [x] **Smoke tests cobrindo os cenários principais.** Executar e documentar no Execution Log:
  - Windows puro com Google Drive Desktop → detecção + symlink + JSON.
  - macOS com iCloud + Google Drive simultâneos → menu lista ambos.
  - WSL sem rclone → wizard instrui install; ao re-rodar, completa fluxo.
  - WSL com mount rclone dormindo → `*doctor` espera cold start, retorna PASS.
  - Linux puro com systemd-user unit → mount persiste após reboot da sessão.
  - Provedor ambíguo (dois GoogleDrive-{conta} no Mac) → menu pergunta qual.
  - Path manual via "Outro/Custom" → fallback preserva comportamento Fase 1.
  - Idempotência: dois runs consecutivos sem duplicação.

## Fora de Escopo

- Habilitação automática de systemd no WSL — apenas instrução documentada com edição manual de `/etc/wsl.conf` + `wsl --shutdown` no host.
- Instalação automática de rclone — apenas instrução por OS; o usuário executa.
- OAuth de provedor dentro do Kairos — segue delegado ao app nativo do provedor ou ao `rclone config` interativo.
- Suporte a outros backends de sync além de symlink (ex: rsync, FUSE customizado, S3 direto).
- Migração de `cloud-sync.json` gerado pela Fase 1 — formato é totalmente compatível, leitura adicional sem rewrite.
- Substituir o flag de eleição (`pwsh -Verb RunAs`) usado em `install.ps1` para criar symlink sem Developer Mode — fluxo de elevation existente é preservado.
- Detecção/configuração de provedores além dos 4 mainstream + rclone (Box, Mega, pCloud etc. ficam acessíveis apenas via rclone).

### Decisões tomadas

- **Helper functions em install.sh definidos inline antes do uso**: Bash não tem mecanismo de forward-declaration limpo; as funções `_rclone_*` são definidas no início da seção cloud sync, antes do code de detecção, para não poluir o escopo global do script.
- **`New-KairosSymlink` como function PS em vez de bloco inline**: O bloco de elevação UAC era duplicado entre a versão PS da seção e qualquer futura reconfiguração. Extraiu-se como function reutilizável.
- **Polling não-recursivo em bash**: Optou-se por array de delays `(0 1 2 5 10 15)` com for-loop em vez de `while true + sleep + counter` para facilitar leitura e evitar loop infinito acidental.
- **Provider como `rclone:{remote}` no JSON**: Segue a convenção do AC (ex: `rclone:drive`), o que permite ao `*doctor` identificar providers rclone com simples `startswith("rclone:")`.
- **Passo 1.5 como condicional dentro da task**: O passo 1.5 é `(condicional)` no título, não um passo numerado fixo — isso evita renumeração dos passos existentes e mantém compatibilidade com leitores do arquivo.
- **Smoke tests documentados no Execution Log** em vez de scripts separados: os cenários não são automatizados (requerem hardware real com mounts), então foram documentados aqui para que o `@kairos *review` possa verificar cobertura.
