## Objetivo

Tornar `*new-squad`, `*update-squad`, `*new-story` e `*new-epic` acessíveis a dois perfis distintos de usuário: quem já sabe o "como" (perfil técnico — hoje bem servido) e quem tem clareza do "porquê / o que quer alcançar", mas não pensou ainda em agentes, pipelines ou critérios de aceite. O @kairos deve derivar a estrutura técnica a partir de uma descrição de propósito, não exigir que o usuário saiba as respostas de antemão.

## Contexto

Os quatro comandos afetados têm hoje um padrão de elicitação estruturada em perguntas sequenciais — útil para usuários técnicos que já sabem exatamente o que querem criar. Mas quando o usuário descreve o objetivo em linguagem natural ("quero um squad que me ajude a monitorar oportunidades no LinkedIn"), ele não sabe de antemão quantos agentes criar, quais comandos cada um vai ter, ou quais são os critérios de aceite. A elicitação atual não tem um caminho para esse perfil.

Adicionalmente, `*update-squad` ainda pede a estimativa de complexidade ao usuário — decisão que o @kairos pode e deve tomar com base na mudança descrita.

O padrão a instituir: **"Se o usuário descreve o propósito, o Kairos deriva a estrutura. As perguntas são um fallback, não o caminho principal."**

## Critérios de Aceite

### *new-squad

- [x] A task `kairos-new-squad.md` documenta explicitamente dois modos de entrada:
  - **Modo propósito**: o usuário descreve o que quer alcançar com o squad (em linguagem livre); o @kairos deriva nome, agentes, pipeline, frequência e integrações; exibe proposta consolidada para confirmação antes de criar qualquer arquivo
  - **Modo guiado**: elicitação sequencial atual (Blocos 1–4), invocado quando o usuário responde à pergunta inicial com perguntas ou diz que não sabe por onde começar
- [x] O ponto de entrada do `*new-squad` começa com uma única pergunta aberta: "Descreve o que este squad vai fazer ou qual problema resolve. Pode ser livre — o Kairos cuida do resto." — em vez de ir direto para "Bloco 1 — Nome"
- [x] No modo propósito, o @kairos deriva e propõe todos os campos do Bloco 1–4 na confirmação consolidada ("Vou criar o squad com esta arquitetura"); o usuário pode aceitar, ajustar pontualmente, ou pedir reelicitação guiada campo a campo
- [x] O modo guiado permanece idêntico ao atual (nenhuma pergunta removida), ativado quando o usuário diz que precisa de ajuda para estruturar ou quando a descrição livre for insuficiente para derivar uma arquitetura razoável

### *update-squad

- [x] A task `kairos-update-squad.md` remove a "Pergunta 5 — Complexidade" da sequência de elicitação
- [x] O @kairos deriva a complexidade com base no aspecto elicitado (Pergunta 1) e na descrição da mudança (Pergunta 2), usando a heurística: P = ajuste de instrução ou texto em um arquivo; M = múltiplos arquivos ou novo comportamento em agente existente; G = novo agente, nova task ou mudança de pipeline
- [x] A complexidade derivada é exibida na confirmação final como informação (não como pergunta): "Complexidade estimada: {P|M|G} — {razão em uma frase}"
- [x] Se a estimativa for ambígua (ex: mudança que pode ser M ou G dependendo do escopo), o @kairos pode perguntar uma única pergunta de desambiguação, não a pergunta genérica de complexidade

### *new-story

- [x] A task `kairos-new-story.md` documenta que a entrada pode ser uma descrição livre do objetivo (ex: "quero rastrear quando o n8n falha") em vez de respostas sequenciais a cada campo
- [x] Quando o usuário fornece uma descrição livre, o @kairos deriva: epic provável (apresenta para confirmação), type (default: instance), título, ACs (mínimo 3), fora de escopo (o que naturalmente não faz parte), complexidade (P/M/G com razão), e dependências (se detectáveis da descrição)
- [x] A proposta derivada é exibida consolidada para confirmação antes de criar o arquivo — o usuário pode editar campos individualmente, não precisa redigitar tudo
- [x] O fluxo de perguntas sequenciais (atual) permanece disponível: ativado quando o usuário pede ("me faça as perguntas") ou quando a descrição não contém informação suficiente para derivar os campos
- [x] A task documenta explicitamente que ambos os fluxos existem e quando usar cada um

### *new-epic

- [x] A task `kairos-new-epic.md` documenta que a entrada pode ser uma descrição livre do objetivo do epic
- [x] Quando o usuário descreve o objetivo em linguagem livre, o @kairos deriva: tema, objetivo formal, critérios de conclusão (mínimo 3), status inicial (default: Backlog), stories candidatas (se mencionadas), dependências (se mencionadas)
- [x] A proposta derivada é exibida consolidada para confirmação ("Vou criar o epic com estas informações") — o usuário pode editar antes de criar
- [x] O fluxo de perguntas sequenciais permanece disponível como fallback (ativado por pedido explícito ou por descrição insuficiente)

## Fora de Escopo

- Alterar o formato dos arquivos gerados por qualquer um dos quatro comandos (squad.yaml, story.md, epic.md) — apenas a elicitação muda
- Modificar `*implement`, `*review`, `*pre-push` ou qualquer outro comando do @kairos
- Adicionar modo yolo-específico a esses comandos — o modo yolo já lida com elicitação autônoma via `yolo_mode.autonomous_behavior`
- Alterar o comportamento pós-elicitação (confirmação, scaffolding, auto-criação de story no *new-squad, etc.)
