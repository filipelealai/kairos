## Objetivo

Reorganizar as três tasks de release (`*pre-push`, `*push`, `*version`) em escopos disjuntos: `*pre-push` vira validação pura (gate de review por `type` da story + spot check), `*push` absorve doctor, prompt "modo dev", transição Done e commit, e `*version` (kairos-version-bump.md) passa a ser a única autoridade de bump (com `*doctor` como Passo 1, sem commit). Adiciona CI workflow `version-guard.yml` como gate canônico de versionamento antes de `origin/main`, espelhado em `push-dual` para a rota direta.

## Contexto

`kairos-pre-push.md` mistura validação, doctor, bump, SHA-sync, frontmatter, commit e transição Done — produzindo dois problemas:

1. **Versionamento acoplado a validação local:** pre-push exige bump mesmo quando a mudança não vai a `origin/main`, gerando atrito desnecessário em forks/instâncias. Versionamento só importa quando o conteúdo de framework vai para o repo público.
2. **Gate de review depende do bump_type:** a heurística atual ("é MINOR/MAJOR? então pede gate") força o usuário a pensar em versão para passar pelo gate. O dispositivo correto é a `type` da story (kairos-core requer gate; instance é auto-revisada por `*implement`).

A nova arquitetura distribui responsabilidades:

- `*pre-push` = validação pura, sem efeitos colaterais (sem commit, sem doctor, sem bump). Idempotente.
- `*push` = orquestrador de release: detecta escopo via manifest, exibe prompt "modo dev?" se há mudanças framework, invoca `*version` inline em modo dev, faz transição Done, comita, empurra.
- `*version` = autoridade única de bump, com `*doctor` como Passo 1. Standalone OU embutido em `*push`.
- `*push-dual` = espelho de `*push` + sync framework→main + `version-guard.sh` antes do push para `origin/main`.
- CI `version-guard.yml` = gate canônico em PRs para main (Checks A: bump, B: frontmatter, C: CHANGELOG, D: gate review).

## Dependências

**Epic 7 deve estar concluído antes desta story.** Em particular:

- **Story 7.2 (Tagging automático no `*pre-push` + backfill one-shot):** adiciona ao `push-dual` a criação automática de tag Git após push para `origin/main`, validação cruzada CHANGELOG vs `core-config.yaml`, HALT se tag já existe, e **guard de Git no início de `*version`, `*pre-push`, `*push` e `push-dual`** (HALT se Git ausente, com instruções de instalação por SO). Esses comportamentos devem ser **preservados** pela refatoração da 3.31:
  - Guard de Git: continua existindo em todas as quatro tasks. Na nova arquitetura, o guard de `*pre-push` só importa quando há story `type: kairos-core` In Review (rota com Git); em scope=instance-only o guard é trivialmente atendido (Git pode estar ausente — não chega a usar). Em `*push` e `*push-dual`, guard roda sempre. Em `*version`, guard roda como pré-pré-condição (antes do Passo 1 doctor).
  - Tag automática em `push-dual`: continua acontecendo após push para `origin/main`, agora num push-dual já reestruturado com Passo 0e (version-guard.sh) antes do commit/push.
  - Validação cruzada CHANGELOG vs core-config: hoje em `*pre-push`; nesta story, migra para o CI `version-guard.sh` Check C e para o próprio `*version`.
- **Stories 7.1 e 7.3-7.6:** não tocam estruturalmente em `*pre-push`/`*push`/`*version`, mas o epic 7 inteiro deve estar Done para evitar conflito de merge e retrabalho — várias stories alteram arquivos próximos.

Stories anteriores que tocam pre-push e estão Done (3.9, 3.10, 3.14, 3.17, 3.19, 3.20, 3.24, 3.25, 3.30): esta refatoração consolida a lógica madura delas e a redistribui — não bloqueia.
