## Objetivo

A story 3.18 implementou derivação automática de descrição para o CHANGELOG, mas produziu dois problemas concretos observados no primeiro uso: (1) quando múltiplas stories PATCH são acumuladas antes de um push, o `*pre-push` cria um bump por story — gerando entradas redundantes no CHANGELOG e versões desnecessárias (`3.1.5 → 3.1.6 → 3.1.7`); (2) a descrição gerada é apenas uma lista de arquivos modificados (`kairos-pre-push.md, CHANGELOG.md: atualizado`), sem valor semântico. Esta story corrige os dois problemas.

## Critérios de Aceite

- [x] O step 4 (PATCH) de `kairos-pre-push.md` não itera story por story: ao detectar múltiplas stories PATCH com gate não-commitado no mesmo ciclo, consolida em **um único prompt** cobrindo todas:
  ```
  ⚠️  Stories PATCH pendentes de bump: {id1}, {id2} — deseja bumpar agora? (s/n):
  ```
  Um único `s` gera UM bump e UMA entrada no CHANGELOG descrevendo as mudanças de todas as stories juntas.

- [x] O step 2.d de `kairos-pre-push.md` (MINOR/MAJOR) e o caminho PATCH (quando chama step 2.a–2.e) invertem a prioridade da derivação de descrição:
  1. **Execution Log** (novo primeiro): para cada story ativa com `## Execution Log → ### O que foi feito`, pegar o primeiro bullet (sanitizado: remover `(story X.Y)`, `story X.Y`, títulos entre aspas); para múltiplas stories (PATCH consolidado), concatenar os primeiros bullets separados por `"; "`
  2. **Git diff × manifest** (era primeiro, agora segundo): `{basename1}, {basename2}: adicionado|atualizado`
  3. **Fallback**: `"ajuste de instrução no framework"`

- [x] A descrição no CHANGELOG reflete o QUE mudou funcionalmente — não apenas "arquivo X: atualizado". Exemplo esperado para o caso 3.15+3.18:
  ```
  - kairos-pre-push.md: entradas neutras no CHANGELOG sem referências de instância; derivação automática de descrição via git diff × manifest
  ```

- [x] Para bump de story única MINOR/MAJOR (step 2.d): o comportamento é o mesmo — usa Execution Log do step 2.d como prioridade 1 ao derivar a descrição.

- [x] Nenhum caminho produz múltiplos bumps para stories acumuladas no mesmo ciclo de push (sem commit entre elas).

## Fora de Escopo

- Alterar a lógica de detecção de stories MINOR/MAJOR no step 1 e step 2 (esses já funcionam corretamente por serem obrigatoriamente uma story por push)
- Mudar o formato semver ou categorias do CHANGELOG (Adicionado/Alterado/Corrigido)
- Detectar automaticamente a categoria da entrada (Adicionado vs Corrigido vs Alterado) — usar `### Corrigido` como default para PATCH, mantendo comportamento atual

## Notas de Implementação

**Sobre a consolidação (AC 1):**

No step 4, em vez de iterar e perguntar por story, o algoritmo deve:
```
1. Coletar todas as stories PATCH com gate PASS/RESSALVA onde epoch_changelog <= epoch_gate
2. Se a lista tiver 1 story: prompt singular como hoje (mas sem loop)
3. Se a lista tiver > 1 story: prompt consolidado listando todos os IDs
4. Se o usuário responder "s": executar UM bump (passos 2.a–2.e) com descrição consolidada
```

**Sobre a descrição semântica (AC 2 e AC 3):**

Para derivar o primeiro bullet do Execution Log de cada story:
```
1. Para cada story ativa (as que dispararam o prompt):
   - Leia docs/stories/{story-id}.story.md
   - Localize "## Execution Log" → "### O que foi feito"
   - Pegue o primeiro item de lista (linha iniciada com "- ")
   - Sanitize: remover "(story X.Y)", "story X.Y", backticks de paths, texto entre aspas duplas

2. Se múltiplas stories: concatenar os bullets sanitizados separados por "; "
   → descrição = "{bullet_story_A}; {bullet_story_B}"

3. Se nenhuma story tem Execution Log: fallback para git diff × manifest
```

**Nota sobre categoria CHANGELOG:** PATCH usa `### Corrigido` por default — não mudar isso nesta story.
