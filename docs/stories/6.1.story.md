## Objetivo

Implementar o servidor MCP do Kairos como entregável de código: servidor Node.js/TypeScript usando `@modelcontextprotocol/sdk`, contêiner Docker pronto para deploy em Swarm com labels Traefik, documentação completa para o time, e plano operacional detalhado para a próxima fase de deploy.

Esta story entrega tudo que pode ser feito sem ações externas — DNS, Service Account no Google Cloud, secrets em produção, validação end-to-end com membro real do time são escopo da Story 6.2.

A entrega é validada localmente via smoke test: servidor sobe, lista corretamente os agentes operacionais (excluindo `@kairos`), responde ao protocolo MCP via HTTP, autentica via Bearer token.

## Notas de Implementação

**Sobre o transport MCP:** o SDK oferece três transports — stdio (local), SSE (deprecado) e StreamableHTTPServerTransport (atual). Optei por Streamable HTTP em modo stateless (`sessionIdGenerator: undefined`), o que significa que cada request POST cria seu próprio transport. Suficiente pro caso (Claude Desktop reabre conexão por conversa) e elimina state de sessão a gerenciar.

**Sobre `tsx` direto vs `tsc` build:** o Dockerfile roda `tsx` direto em vez de pré-compilar com `tsc`. Custo: ~50MB extras na imagem e startup ~200ms mais lento. Benefício: zero overhead de iteração — alterações no código requerem só restart do contêiner, sem rebuild. Aceitável para servidor longo-vivo.

**Sobre whitelist em vez de blacklist:** a restrição de governança é implementada como **whitelist** (apenas agentes em `core-config.yaml > agents.squads.{*}.agents[]` aparecem como prompts MCP) em vez de blacklist (excluir explicitamente `@kairos`). Razão: defensivo. Se algum dia for criado um novo agente de governança, ele não vaza por padrão — só vaza se for adicionado a um squad ativo, o que seria intencional.

**Sobre o pattern `_FILE`:** `config.ts` faz expansão automática — se `KAIROS_MCP_API_KEY_FILE=/run/secrets/foo` está setado e a env `KAIROS_MCP_API_KEY` não está, lê o conteúdo do arquivo e popula a env. Isso permite que o `docker-stack.yml` use Docker Swarm secrets corretamente, mantendo as chaves fora de `docker service inspect`.

**Sobre falha do Drive não bloquear `save_output`:** se o Drive der erro (quota cheia, credenciais expiradas, rede), o output local ainda é salvo no contêiner e o tool retorna `drive: null`. Isso evita perda de trabalho do agente. Log warn registra o erro pra debug posterior.

### Decisões tomadas

- **Streamable HTTP stateless:** cada POST cria transport novo. Mais simples, sem state de sessão, suficiente pro caso. Trade-off conhecido: não suporta server-push de longa duração (não é necessidade hoje).

- **Whitelist em vez de blacklist:** decisão defensiva — só agentes explicitamente listados em squads ativos aparecem. Se um novo agente de governança for criado no futuro, ele não vaza por padrão.

- **`tsx` direto no contêiner sem `tsc` prévio:** simplifica iteração ao custo de ~50MB de imagem. Aceitável.

- **`_FILE` pattern para secrets:** essencial pra Docker Swarm secrets funcionarem corretamente. 10 linhas de código no config.ts.

- **`save_output` paralelo (local + Drive) com falha do Drive não bloqueante:** se Drive falhar, output local ainda é salvo. Evita perda de trabalho.

- **Long-running script via job-id + state in-memory:** simples, sem Redis. Limitado a 50 jobs. Suficiente pra v1.

- **Documentação do time em `squads/team-setup.md` (não em `squads/ops/docs/`):** decisão arquitetural do usuário durante a sessão — é um documento transversal aos squads, não pertence ao escopo de `ops`.

- **Split da story original em 6.1 (código) + 6.2 (deploy):** decisão tomada com o usuário durante a sessão. A story original assumia entrega única, mas o escopo aditivo do epic justifica a separação. Permite revisão e push do código antes da Fase 2 acontecer.
