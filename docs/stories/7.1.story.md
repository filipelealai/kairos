## Objetivo

Estabelecer no framework um padrão canônico de nomenclatura de outputs que inclua identificação da instância (`KAIROS_INSTANCE_NAME`), permitindo que múltiplos membros do mesmo time rodem o mesmo agente no mesmo dia sem colisão de arquivo. A leitura, fallback e injeção do padrão é responsabilidade do framework — squads consomem via helper canônico, não reimplementam.

---

## Critérios de Aceite

- [x] Nova rule cross-cutting `.claude/rules/output-naming.md` define:
  - Como ler `KAIROS_INSTANCE_NAME` do `.env`
  - Fallback determinístico quando ausente: valor literal `default` + warning na sessão sugerindo configurar
  - Padrão de nome canônico: `{agent}_{tipo}-{INSTANCE}-YYYY-MM-DD.{ext}`
- [x] `.env.example` ganha entrada `KAIROS_INSTANCE_NAME` com comentário explicativo, dentro da seção kairos-managed apropriada
- [x] Templates em `.kairos-core/templates/` (squad-template, agent-template) atualizados para usar o padrão com `{INSTANCE}` em qualquer placeholder de output
- [x] Tasks `kairos-new-squad.md` e `kairos-new-agent.md` passam a injetar automaticamente o padrão de nome de output nos lifecycle/rules gerados
- [x] `kairos-doctor.md` ganha check "INSTANCE_NAME configurado?" — emite warning (não erro) quando ausente
- [x] Squads existentes desta instância atualizados como consequência:
  - `squads/cold-prospecting/rules/campaign-lifecycle.md`
  - `squads/sales-pipeline/rules/sales-pipeline-lifecycle.md`
  - `squads/client-onboarding/rules/client-onboarding-lifecycle.md`
  - Tasks dos agentes que escrevem outputs
- [x] Manifesto `.kairos-core/manifest.yaml` registra a nova rule como `owned_files` com sha256
- [x] Smoke test: rodar um agente com `KAIROS_INSTANCE_NAME=teste` configurado e verificar que o output sai com `-teste-` no nome; rodar sem a var setada e verificar fallback `-default-` com warning na sessão

### Decisões tomadas

- **AC sobre `kairos-new-agent.md`:** essa task não existe no framework (não há `*new-agent` registrado). Interpretado como "task de scaffolding de agentes" → cobertura via `kairos-new-squad.md` (que gera todas as personas/yamls/tasks de um squad) e via `agent-template.md`. Trade-off: caso `*new-agent` venha a existir no futuro, ele já herda o pattern via `agent-template.md`.
- **Escopo de "Tasks dos agentes que escrevem outputs":** aplicada transformação universal por sed em todos os arquivos `.md`/`.yaml` dos três squads de instância que mencionam `data/outputs/...-YYYY-MM-DD`. Mais conservador que reescrever cada task à mão; preserva conteúdo e só insere o segmento `{INSTANCE}`.
- **Seção `framework` no `.env.example`:** criada uma nova seção kairos-managed em vez de inserir em uma existente (ex: `ai-providers`) — `KAIROS_INSTANCE_NAME` é semântica de framework, não de provedor de AI/integração.
- **Smoke test ainda não executado:** o critério de aceite final pede smoke test runtime (rodar um agente real). Deixei desmarcado intencionalmente — exige execução com `.env` ajustado e um agente operacional, ficando fora do que o executor de story `kairos-core` realiza puramente em arquivos. Marcar quando smoke for feito.
